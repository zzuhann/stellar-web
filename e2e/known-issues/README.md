# e2e/known-issues/ — 故意紅的測試

## 這個目錄在幹嘛？

這裡的測試**現在是紅的，而且是故意的**。

它們斷言「產品應有的正確行為」，而產品目前**還沒做到**。所以它們會失敗（紅燈）。
當某一條變綠，代表工程師把那個 bug 修好了。

**CI 不會因為這個目錄的紅燈擋 merge**（由獨立的執行指令跑，exit code 不計入主流程，見專案根目錄 `playwright.config.ts` 的 `known-issues` project 與 `package.json` 的 `test:e2e:known`）。

## 這個目錄的價值 = 一個乾淨的訊號

**紅燈數量 == 待修 bug 數量。**

PM 直接把這個數字拿去跟工程師溝通「還有幾個確認過的缺陷沒修」。
一旦混進「不是產品缺陷」的失敗，這個數字就失真、訊號就廢了——所以准入標準很嚴。

## 准入標準（嚴格遵守）

✅ **只有一種東西可以進來**：已在**正式站**經**人工確認過**的**產品缺陷**
　（測試斷言的是正確行為，產品目前確實不符）。

❌ 以下一律**不准**放進來，它們是「測試壞了」不是「產品壞了」：

- 因為**路由改名 / 選擇器過期 / 寫法過時**而失敗的測試
- 因為**資料空窗期**（例如當下剛好沒有符合條件的資料）而失敗的測試
- **還沒在正式站確認**、只是「我覺得可能有問題」的測試 → 先回報 PM，由 PM 上站確認，別直接丟進來

## 一條測試變綠了，該怎麼辦？

代表對應的產品缺陷已修復。請：

1. 再次確認正式站行為確實已修正（避免是暫時性或環境造成的綠）。
2. 把該測試**搬到 `e2e/regression/`**（它從此屬於「應該永遠綠」的回歸集）。
3. 調整 `@scenario` 標記：把 `known-issue` 字樣移除。

## 撰寫慣例（與 regression/ 一致）

- `@scenario` 標記格式：`// @scenario A-5 known-issue`
- test 標題寫成完整句子（在哪裡、做什麼、應該怎樣）
- 每個斷言帶自訂失敗訊息（PM 會直接把訊息貼給工程師）
- 外部連結只驗 href + target + rel，不點出去
- 選擇器沿用既有慣例，不用 PandaCSS 自動 class
